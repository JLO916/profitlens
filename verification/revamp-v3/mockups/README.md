## 3 設計稿與 PRD 的差異（請審查者特別看）

1. **拆解標題和本期一句話的「最大一項」不一致**。PRD 的範例標題是「少賺 59.9 萬，最大一項是折扣（−118.8 萬）」，但示範資料的九項裡扣最多的是商品成本（−157.5 萬），折扣排第二。設計稿的拆解標題改寫成「少賺 59.9 萬，扣最多的一項是商品成本（−157.5 萬）」，本期一句話仍照 PRD 模板用三件事第一名（折扣多花 118.8 萬）。同一畫面出現兩種「最大」會不會讓人困惑，見問題 Q5；**待確認**：拆解標題要取九項的最大扣項，還是沿用三件事第一名。
2. **本期利潤結構的扣項全部用不利色**。PRD §10.3 只寫「商品成本（不利）」，沒有寫其他扣項；設計稿把所有扣項（商品成本、平台抽成、金流、物流、其他、廣告）都畫成不利色。這張圖是結構不是變化，紅色會不會太多，見問題 Q6。
3. **期間列沒有選中的快捷**。示範資料的兩期是自訂的 42 天，五個快捷都沒有對上，所以沒有選中狀態；手機的期間按鈕寫「自訂期間 · 7/13–8/23」（PRD 範例寫「近 4 週」）。「近 12 週」「本月 vs 上月」「去年同期」因資料不足設為停用，去年同期的理由用一行 12px 文字放在期間列下方。
4. **手機版隱藏頁首**。依 §7.0「390×844：48px 頂欄加 40px 期間按鈕，下面就是內容」，手機的 h1 只留給螢幕報讀器，「匯出本頁」移到「更多」。會議紀錄頁例外，手機仍顯示頁首動作列（決議狀態、複製、匯出會議）。
5. **「廣告佔比」用 `copy-rewrite.csv` 的名稱**（PRD §7.1 第 9 點的表格寫「廣告佔淨營收」）。
6. **每週趨勢畫了四條線**（淨營收、扣廣告後貢獻 × 本期、上期），用直接標籤區分；圖上方的兩個大數字只放淨營收。
7. **各通路圖的標題寫結論句**「平台 · MARKETPLACE 扣完廣告虧 6.1 萬」（C16 的規則），標準名稱放副標。
8. **抽屜的階梯公式從商品原價收入一路寫到扣廣告後貢獻**（PRD 範例只寫最後一步）；原始明細的「欄位與數值」用中文欄名（PRD 範例用英文 key）；本期的銷售列數是 1,680（v2 的影響類抽屜同時列兩期，所以是 3,360）。
9. **會議紀錄只畫已結束狀態**。草稿狀態的決議 select 與「結束會議」主要按鈕沒有畫出來。
10. **只畫靜態畫面**：選單、popover、底部面板（期間、更多）沒有畫開啟狀態；768 與 1280 寬有對應的 CSS，但沒有附截圖。

## 4 審查方式

- 每位審查者獨立評分，約 30–45 分鐘，不互相討論後再填。
- 順序：先看 `shots/overview-1440.png` 做 Q1（10 秒），再依序開三份 HTML（桌機），最後看 390 截圖或把視窗縮窄。
- 每題 1–5 分，寫一句理由；看到具體問題，寫「頁面＋位置＋問題」。
- 設計者另外看 `tokens.css` 與顏色、間距的一致性。

## 7 通過條件

PRD 沒有為 H2 訂通過條件（H1／H4 的可用性測試用 7 點量表，目標是專業感平均 ≥ 5.5、AI 感平均 ≤ 3.0，見 `docs/revamp-v3/usability-test.md`）。本設計稿提議：

- **Q2 專業感中位數 ≥ 4**，而且 **Q3 AI 感中位數 ≤ 2**。
- 其他題的中位數 ≤ 2 時，列為 V3-3 開工前必修。
- 具體問題中，與 PRD 衝突或需要改 PRD 的項目，由使用者拍板後回寫 PRD 或 `09_DECISIONS_PENDING.md`。

**狀態：待確認**（需要使用者同意這個通過條件，才能用來判定 H2）。

## 8 截圖怎麼產生

用 repo 既有的 Playwright chromium（不新增依賴），以 `file://` 開啟三份 HTML，視窗 1440×1000 與 390×844、deviceScaleFactor 1，各存首屏與整頁；抽屜另存捲到底的畫面。產生截圖的小腳本放在工作暫存區，沒有提交。截圖是在 macOS 上產生，中文字型是 PingFang TC；Windows 的正黑體會略寬。
